# Tooling

- Prefers compact, human-friendly duration display in status bars/scripts over verbose breakdowns: durations ≥24h shown as whole days rounded up (e.g., anything from 25d up to <26d displays as `26d`), durations <24h shown in hours (e.g., `3h`), and durations <60min shown in minutes (e.g., `35m`). Confidence: 0.7
- Wants usage/credit stats for all the AI tools they use (Claude, Codex, Command Code, DeepSeek, Antigravity, etc.) consolidated in the tmux status bar as compact segments driven by one shared script (`tmux-usage-bar.py`), not separate per-tool bars. Confidence: 0.7
- Wants the tmux status bar kept as narrow as possible: drop redundant labels (e.g., `GPU`), use short Korean forms (`램` for RAM), and remove spaces around separators — e.g. `램4GB|63°C` instead of `RAM 4GB | GPU 63°C`. Confidence: 0.7
- For status-bar segments of cancelled/unavailable services, keeps the entry in config (explicitly no delete) but moves it to the end of status-left so it is truncated first when the screen is narrow. Confidence: 0.6
- Erroring/disabled status-bar segments should be visually marked as "deactivated" via a gray theme (with strikethrough when supported) instead of showing normal-color error text — e.g., gray `CC e85` for a cancelled Claude entry. Confidence: 0.6
- Prefers FastAPI for new web dashboards/viewers (explicitly requested over the existing Flask app in the repo). Confidence: 0.9
- Uses FastAPI WebSocket endpoints (`fastapi.WebSocket`) to push server-driven updates, with the REST handler's snapshot-building logic extracted into a shared helper (`_targets_snapshot()`) so REST and WebSocket stay consistent. Confidence: 0.7
- Wants launcher scripts to run with `uvicorn[standard]` (for websockets support) and expects cross-platform launcher scripts (web.sh / web.bat) to be updated in tandem with new runtime dependencies; shell launchers should pass complex uv args (e.g., `'uvicorn[standard]'`) via `exec`/env-var style rather than a PY string re-parsed by the shell, to avoid quote-stripping bugs. Confidence: 0.7
- Wants web UIs in a clean Google Material style, mobile-first and mobile-friendly (responsive viewport, mobile-tested alongside desktop). Confidence: 0.9
- Wants cross-platform launcher scripts at the repo root for runnable tools — both `web.sh` (Unix) and `web.bat` (Windows). Confidence: 0.8
- Wants result dashboards structured as drill-down views: overview list (bench, run, attempted, resolved, score) → per-bench detail → per-instance detail (problem statement + solution trajectory). Confidence: 0.7
- Dashboards must never show misleading zeros: when the canonical eval summary (eval/summary.json) is missing, aggregate counts directly from the available per-instance result artifacts (e.g., tb20__*.json verdicts) and never treat internal layout dirs (archive/eval/logs/predictions) as benchmarks — the displayed numbers must always reflect what is actually recorded on disk. Confidence: 0.6
- Wants each benchmark experiment tagged in the dashboard with its full experiment-target metadata — model name, model URL, server start script, and bench run script (showing the last tuned/renamed version when scripts are updated) — because the hardware runs only one model at a time and experiments are frequently interrupted to swap models. Confidence: 0.8
- Script/status references in the dashboard must be clickable and reveal raw content, not just names: a RUNNING badge placed inline right after the model URL opens a modal with the server start script name + full content (read from the remote host) and the live `<url>/models` response as pretty-printed JSON; each run row is formatted `run-id <bench start script> <spinner>` where the bench script link opens the archived script's full content. Confidence: 0.7
- Wants currently-running benchmarks clearly flagged in the dashboard with a spinner/animated progress bar so active work is visually distinguishable from finished runs. Confidence: 0.8
- A run's client bench script link should itself carry the running indicator: the same pastel-green background pill as the up endpoint plus the literal word "running" appended after the script name (e.g., `tune003-start-swebench-verified.sh running`), not only a separate spinner chip. Confidence: 0.8
- Wants maximally dense dashboard rows: merge label/value pairs into a single line (e.g., `Model <model> <spacer> <url>` replacing separate Model / Model URL lines) and prefers one small icon (●) over a text badge ("RUNNING") — explicitly asked to "save output line count" (출력 라인 수를 아끼자). Confidence: 0.8
- Server up-status should be live-probed from the actual model URL (`GET <url>/models` with a short timeout and cache) and shown consistently on every entry that references that URL, so all sections pointing at the same running server display the same up icon. Confidence: 0.6
- Attributes "currently running" to runs by bench-script identity: every run whose bench script matches the currently executing script gets the running icon, not only the single active run folder. Confidence: 0.6
- Defines a "run" by the (bench official name + model name + model URL) triple — repeated executions with the same triple must accumulate into the same run folder (run-1, run-2, …) until the user manually starts a new run via a future "New Run" action; the dashboard list is run-unit based, so multiple benches must not be lumped under a single run id. Confidence: 0.9

- Wants the dashboard to auto-update close-to-real-time via a WebSocket endpoint that periodically pushes full state snapshots (server up status, loaded model info, running bench, run stats) so both the landing list and the run-detail view refresh without manual page reloads; periodic push/polling refresh is preferred over static pages. Confidence: 0.8
- Run-detail page status pills are placed inline immediately after their referent — `RUNNING` right after the bench script filename, `UP` right after the model URL — and are toggled in place from the WebSocket snapshot data (added when true, removed when false); negative states render nothing at all (server down → no pill; not running → no RUNNING pill), unlike the landing list which shows a gray DOWN pill. Confidence: 0.8
- Backend run-detail API responses should carry the same live status fields the WebSocket snapshot provides (e.g., `server_up`), so the initial render of the run page matches the WS-driven state instead of showing a stale/blank indicator until the first push. Confidence: 0.5
