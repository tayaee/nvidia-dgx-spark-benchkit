# Workflow

- Iterative run-then-fix loop: run the smoke/test first, fix whatever errors surface, then re-run — not plan-then-build. Confidence: 0.9
- Incremental batches: solve a few problems per benchmark (1 → 3 → 5 → 10), report after each batch, instead of one bulk run; for a brand-new benchmark script, explicitly start with solving just 1 problem to validate the run structure. Confidence: 0.9
- Treats a benchmark run as worthwhile as long as the execution structure was validated (script works, docker verification runs, results land in the right layout) even if every instance failed; prefers moving on to the next benchmark over retrying the failures. Confidence: 0.5
- Runs must skip already-solved items and be resumable (--limit-new=N means "skip solved, solve N new"). Confidence: 0.9
- Remove benchmarks/components that can never run from the list rather than keeping dead entries around. Confidence: 0.8
- "Smoke test" means actually solving a real task end-to-end (execute the model's output, run the canonical verifier) — not just detecting that an artifact was produced. Confidence: 0.9
- Use Docker sandbox execution to actually run and verify model outputs, with the canonical benchmark images (SWE-bench images, per-task terminal-bench images, ECR deep-swe images). Confidence: 0.7
- For research tasks about a tool/product, expects both local CLI help/docs AND online documentation/web pages (official docs, GitHub, web search) to be checked — not just one source. Confidence: 0.7
- Wants research results persisted to a standalone markdown file (e.g., `~/cmdc.credits.md`) for later reference — not just delivered in chat. Confidence: 0.5
- Skip work items already satisfied by the environment (e.g., server already running → don't write/execute its start script); jump straight to the remaining work. Confidence: 0.7
- Wants the full pipeline completed end-to-end in one go (solve → eval → report), not stopping after intermediate artifacts. Confidence: 0.6
- Wants run/how-to instructions for pipelines documented in a `cheatsheet.md` at the repo root (commands, required env vars, result layout, gotchas) so the procedure can be reproduced later — not just delivered in chat. Confidence: 0.6
- When new dashboard features need data that lives on a remote host, reads it over SSH from the app (e.g., server start script content) with graceful degradation to a local path or an explicit error string — rather than hardcoding content or dropping the feature. Confidence: 0.7
- When extending the pipeline to a new benchmark, expects the exact same established flow to be reused ("같은 방식으로": same start/eval/report script pattern, `--limit-new` incremental solving, official evaluator, per-benchmark result layout) rather than a bespoke one-off approach. Confidence: 0.6
- Verifies UI/dashboard work in a real rendered browser (headless Chromium via Playwright, DOM evaluation, mobile + desktop viewports) instead of only checking that files exist or APIs respond. Confidence: 0.8
- Validates real-time/WebSocket behavior by mutating server-side state (e.g., `touch`ing a run's `state.jsonl` to flip its running status) and confirming the open page updates itself within the push interval — not just that a socket connects. Confidence: 0.8
- Frontend auto-refresh must preserve user position: when re-rendering the landing list from a WebSocket snapshot, save and restore the scroll position rather than jumping to the top; run-detail views refresh their summary/stats in place. Confidence: 0.7
- Debugs frontend issues by inspecting runtime behavior in the browser (console/page errors, hashchange events, API fetches, function-call traces) rather than guessing from code. Confidence: 0.8
- When a version/name in the codebase changes (e.g., terminal-bench 2.1 → 2.0), updates every reference everywhere — code keys, instance-id prefixes, tests, docs, and script filenames — while deliberately leaving historical result data (results/) untouched. Confidence: 0.6
- When the requested newer version/URL is unavailable, proceeds with the available version and defers the missing one for later ("2.1은 나중에 하자") rather than blocking the task. Confidence: 0.5
- Runs benchmark execution scripts in a dedicated third terminal (세번째 터미널) of the terminal layout. Confidence: 0.4
- Wants new pipeline options added uniformly to ALL benchmark scripts (via the shared benchmark-lib.sh, not per-script), with default-off semantics that keep existing invocations unchanged: `--limit-new-ok N` (0 = disabled, no ok-checking), `--limit-max-try N` (0 = unlimited), and `--limit-new-any` as a synonym for `--limit-new`. Confidence: 0.7
- Prefers explicit fail-fast errors over silent resolution when flags conflict: specifying both `--limit-new[-any]` and `--limit-new-ok` must abort with an error ("둘 다 지정하면 에러") instead of letting the last flag win. Confidence: 0.7
- Validates benchmark pipelines by retrying up to N distinct problems until one actually succeeds — stop at the first success, bounded by a max-try cap — and failed instances should be skipped on retry (`.attempted` tracker / `--skip-ids`) so each attempt is a new problem rather than re-running the same one. Confidence: 0.7
- When functionality will be wired up later, prefers shipping the UI affordance now as a mock link that shows a "to be implemented" placeholder on click, rather than omitting it or half-implementing it. Confidence: 0.7
- Dashboards list top-level items (test targets) sorted by most recently updated first, with runs nested inside a target listed in ascending numeric order (run-1, run-2, …). Confidence: 0.8
- Designs benchmark tooling around the reality of a single model server: stopping a run, taking the server down, and resuming an arbitrary other run (bring server up + re-run bench) must be structurally supported because such swaps happen frequently. Confidence: 0.7
- When a supervisor retry loop (web.sh) already manages the web server in another terminal, only kill the server process (web.py) to apply code changes — do not restart the server manually, the loop picks it back up with the new code. Confidence: 0.9
- Wants the running web app itself to be editable from the UI — an "Edit App" flow that collects a plain-language change prompt, dispatches it to a user-selected external coding agent, runs the deploy script, and reports success as `<commit id>` with the commit id as a clickable link opening the git URL in a new browser tab — so app changes can be made online without touching a terminal. Confidence: 0.7
- Reverting a change should produce a new commit that undoes the target commit's content (git-revert style), never a history rewrite/reset. Confidence: 0.7
